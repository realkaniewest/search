# Разрешения, расширения и синхронизация Search

Статус: предложено для проверки. Задача [#112](https://github.com/realkaniewest/search/issues/112). До отдельного принятия действует [ADR 0002](0002-macos-https-preview.md).

## Разрешения сайтов

На macOS нативный обработчик WebKit получает origin, фрейм и тип запроса. Закреплённый интерфейс Wry передаёт Search только тип. До интерфейса разрешений проверить адаптер, который сохраняет схему, хост, порт и сведения о фрейме. Показать источник запроса в нативном диалоге. По умолчанию отказывать, в том числе при смене страницы во время диалога, для вложенного фрейма и при отсутствии сведений об источнике. Существующая политика временных окон остаётся запретом на этом этапе. [WKUIDelegate](https://developer.apple.com/documentation/webkit/wkuidelegate?changes=lat_4&language=objc)

Приёмка первого сценария проверяет два сайта, отдельные решения для камеры и микрофона, отмену при навигации, смену фрейма, отзыв разрешения, перезапуск и временное окно. Геолокацию проверять отдельно через предусмотренный для неё нативный обработчик. Список данных сайтов оперирует именами групп WebKit. Эти имена непригодны для выдачи разрешений по origin.

Проверка на macOS в самом Search подтвердила получение схемы HTTP, хоста 127.0.0.1, порта 43127 и признака верхнего фрейма в нативном обработчике запроса медиа. Камера и микрофон остались закрыты. Наблюдатель включён только в режиме проверки и выводит совпадение с тестовым источником без записи пользовательских адресов. Для повторения использовать `python3 tools/run_search_security_smoke.py --require-media-origin apps/search/target/debug/search-browser` после локальной сборки. Дополнительный прогон первым отправляет запрос микрофона из iframe того же источника. WebKit сообщил тот же адрес и признак вложенного фрейма, страница получила отказ. Запросы из верхнего и вложенного фреймов проверяются в разных процессах, поскольку при повторном запросе из того же WebView уведомление может не поступить. Запрос из iframe на втором порту показал различие между двумя нативными значениями: параметр origin содержал источник верхней страницы, а `WKFrameInfo.securityOrigin` содержал источник iframe. При построении политики нужно сверять оба значения и признак фрейма, используя источник запрашивающего фрейма для решения о доступе. Запрос получил отказ. Проверка допускает ровно один дополнительный локальный URL в режиме проверки. На macOS 27.0.1 отдельный публичный обработчик геолокации WebKit получил источник верхней страницы и инициирующий фрейм. Search вернул нативный отказ, а страница получила `PERMISSION_DENIED`. Повторная проверка подтвердила отказ в iframe того же источника и в iframe на другом порту в обеих тестовых вкладках. Для второго источника параметр origin оставался источником верхней страницы, а `WKFrameInfo.securityOrigin` указывал на второй порт. Для повторения проверку можно запустить с `--require-geolocation-origin` и `--require-media-origin`. На более ранних macOS этот новый обработчик не проверялся. Выдача доступа остаётся за рамками данной проверки. [Обработчик геолокации WebKit](https://developer.apple.com/documentation/webkit/wkuidelegate/webview%28_%3Arequestgeolocationpermissionfor%3Ainitiatedbyframe%3Adecisionhandler%3A%29)

Модель политики в тестах Rust проверяет совпадение канонического HTTPS-origin с данными WebKit и с активным документом, включая номер навигации и идентификатор окна WebView. Разрешения для камеры, микрофона и геолокации хранятся отдельно. Объединённый медиа-запрос требует двух разрешений. Тесты также проверяют восстановление сохранённого решения, отзыв, отказ для iframe и временного окна и невозможность использовать старое решение после перезагрузки или переключения WebView. Модель подключена только к тестам. В отдельном временном каталоге проверена атомарная запись и повторное чтение файла решений. Тест проверяет решение по актуальному файлу профиля. Отзыв в другом окне и удаление файла исключают повторную выдачу из устаревшей копии. Устаревшая копия также не может восстановить удалённый файл. При повреждении файла или ошибке записи решение об успехе не возвращается. Модель ещё нужно связать с реальной навигацией, нативным диалогом и каталогом обычного профиля.

На macOS локальный опыт с нативным листом AppKit проверил показ синтетического HTTPS-origin, кнопку отказа по умолчанию, явное подтверждение и закрытие листа при начале навигации WebKit. Отдельный сценарий доставляет подтверждение после начала перехода и проверяет, что результат отклонён. Запуск: `swift prototypes/macos-permission-sheet/probe.swift`. Опыт использует временный WebView и искусственный запрос. В самом Search подключён отдельный диагностический лист. Нативный запрос верхнего фрейма с проверенным локальным origin открывает лист после отказа WebKit. Тест завершает лист и проверяет, что страница получила отказ. Запуск: `SEARCH_SMOKE_PERMISSION_SHEET=1 python3 tools/run_search_security_smoke.py apps/search/target/debug/search-browser`. Вариант `SEARCH_SMOKE_PERMISSION_SHEET=navigation` начинает новую навигацию при открытом листе. В двух запусках Search получил событие начала загрузки для той же вкладки, закрыл лист с результатом отмены и продолжил проверку с отказом в доступе. В режиме `SEARCH_SMOKE_PERMISSION_SHEET=deferred-geolocation` сам ответ WebKit ожидает закрытия листа. Тест проверяет ровно один отложенный ответ и отказ на странице. При сбросе ожидающего ответа движок также получает отказ. Вариант `SEARCH_SMOKE_PERMISSION_SHEET=deferred-geolocation-navigation` закрывает лист при смене документа, возвращает один отказ для отложенного запроса и проверяет отказ для нового документа. Этот режим существует только для локального тестового окна и не выдаёт разрешений. Режим `SEARCH_SMOKE_PERMISSION_SHEET=deferred-media` проверяет отложенный ответ для первого медиа-запроса. На странице камера и микрофон получили отказ. В режиме `deferred-media-navigation` запрос микрофона открывает лист на локальной странице. Начало перехода закрывает лист, WebKit получает один отложенный отказ, а следующий документ также получает отказ для камеры и микрофона. Маршрут выдачи разрешения и связь с обычным профилем остаются открытыми.

### Условия подключения разрешений к окну Search

- Принимать решение только для активной вкладки обычного профиля. В момент ответа повторно сверять идентификатор WebView, поколение документа и оба нативных origin. Закрытие окна, переключение вкладки и начало перехода отменяют ожидающий запрос.
- Разделять ответ движку и сохранение решения. Одноразовое разрешение действует только для текущего запроса. Постоянное разрешение передаётся движку после успешной записи. Для повторного запроса проверяется актуальный файл обычного профиля. Повреждённый или недоступный файл не даёт доступа.
- В настройках обычного профиля показывать сохранённые решения по сайту и типу доступа. Отзыв убирает выбранное решение из файла. До включения проверить, что после отзыва закрытый и заново открытый сайт действительно получает новый запрос или отказ, включая случай, когда WebKit мог сохранить прежнее решение в памяти. Уже выданный доступ в открытом документе проверяется отдельно.
- Для камеры, микрофона и геолокации подтверждать по отдельности, что WebKit возвращает доступ после явного согласия и отказ при закрытии листа. Отдельно проверить системный отказ macOS, комбинированный запрос медиа, второе окно и приватный режим. Для запроса, который версия WebKit не позволяет безопасно связать с активным документом, сохранять отказ.

## Расширения

Проверить нативный WKWebExtensionController на поддерживаемой версии macOS с тестовым расширением, устанавливаемым явным действием. В карточке установки показывать возможности и сайты, к которым расширение просит доступ. Давать доступ только к подтверждённым сайтам. Загрузку, выключение и удаление проверять на обычном профиле. У тестового расширения нет доступа к внутренней панели, IPC браузера или временным окнам. Заявлять поддержку только для проверенных API и форматов. [WebKit extension controller](https://developer.apple.com/documentation/webkit/wkwebextensioncontroller/configuration-swift.class)

На Mac локальное расширение Manifest V3 выполнило скрипт на разрешённом адресе. Маркер отсутствовал на явно запрещённом адресе, в отдельном WebView без контроллера, загрузившем HTML панели Search, во временном WebView с тем же контроллером и после отзыва разрешения и перезагрузки страницы. Запуск: `python3 prototypes/webkit-extensions/run.py` на macOS 15.4 или новее. Проверка использует локальный сервер и удаляемый профиль. Во вложенном фрейме разрешённого сайта маркер появился только на разрешённом адресе. Тест с тремя отдельными процессами проверил сохранение решения вне непостоянного контроллера, восстановление выдачи доступа и сохранение отзыва после следующего перезапуска. Этот путь требует собственного хранилища решений Search. Для приёмки остаются интеграция с обычным профилем Search, панель в запущенном браузере и IPC.

Дополнительный тест создаёт три WebView через Wry. Собранное на месте расширение подключается только к обычному содержимому с отдельным тестовым UUID. Внутренняя панель Search имеет свой IPC и временное хранилище, у временного содержимого IPC отсутствует. Тест сверяет фактическую конфигурацию движка, запуск скрипта только в обычном содержимом и отсутствие обращений расширения к каналу панели. Запуск: `cargo build --locked --manifest-path apps/search/Cargo.toml --example extension_boundary_smoke`, затем `python3 prototypes/webkit-extensions/run.py --wry-binary apps/search/target/debug/examples/extension_boundary_smoke`. Тот же тест подтвердил, что скрипт прекращает выполняться после выключения расширения и новой загрузки страницы, а после включения снова выполняется. Разрешение по-прежнему действует на другом порту разрешённого хоста. На другом локальном хосте скрипт не выполнялся. После сброса явного разрешения до статуса Unknown расширение осталось загруженным, но скрипт перестал выполняться при новой загрузке страниц на обоих портах. До загрузки тест считывает из WebKit имя, версию, запрошенные возможности и шаблоны сайтов, включая сайты из правил запуска скриптов. После загрузки расширения скрипт впервые выполняется только после явной выдачи доступа к хосту и новой загрузки страницы. Пользовательские расширения и управление ими в основном окне Search ещё не подключены.

Отдельная проверка выявила границу модели WebKit. Выдача через `setPermissionStatus(_:for: URL)` для `http://localhost` на одном порту также разрешила исполнение на другом порту этого хоста, включая вложенный фрейм. Поэтому разрешение расширения в предлагаемой архитектуре нельзя описывать как доступ к точному origin (схема, хост и порт). Перед интеграцией нужно либо согласовать разрешение по схеме и хосту с явным указанием охвата портов, либо показать проверенный способ ограничивать исполнение по origin во всех фреймах.

## Синхронизация

Первый сценарий переносит выбранные браузерные предпочтения и закладки между двумя устройствами. История, данные сайтов, разрешения, локальные пути, содержимое вкладок и временные данные находятся вне этого сценария. Выбор способа синхронизации зависит от доступного подписанного приложения и проверки двумя устройствами.

Для эксперимента с пользовательской папкой iCloud Drive нужны выбор папки в системном диалоге, согласованные файловые операции в фоне, версия формата и обработка параллельных правок. Обычная запись файла с заменой не годится для двух устройств. Проверить правку без сети, конфликт, отмену подключения и обработку повреждённого файла. [Файловая координация Apple](https://developer.apple.com/documentation/Foundation/improving-performance-and-stability-when-accessing-the-file-system)


Локальный прототип проверяет условную запись по идентификатору ревизии внутри NSFileCoordinator. Два процесса с одной исходной ревизией конкурируют за файл, только одна запись проходит. После получения актуальной ревизии повторная операция добавляет закладку и сохраняет изменение оформления. Повреждённый файл остаётся нетронутым. Запуск: `python3 prototypes/macos-settings-sync/run.py`. Опыт использует временную локальную папку. Разрешение конфликтов и доставка файла между устройствами через iCloud ещё требуют проверки.

Для автономной правки прототип сравнивает три состояния: последнюю общую копию, локальную правку и актуальный общий файл. Независимые правки объединяются, разные изменения одного поля дают явный конфликт, а повтор не создаёт новую ревизию. Проверены удаление закладки без её повторного появления при повторе операции и сохранение обеих копий при конфликте. Это имитация автономной правки через локальные файлы, без подтверждения работы File Provider на двух устройствах.

Локальные проверки также подтверждают отказ от неизвестной версии, посторонних полей и HTTPS-закладок с учётными данными. Чтение ограничено размером и обычными файлами. Тест проверяет, что при символической ссылке файл назначения остаётся нетронутым, а при именованном канале операция завершается без ожидания данных. Для интеграции остаются проверка выбранной папки и правила обработки замен файлов, поступивших от File Provider.
