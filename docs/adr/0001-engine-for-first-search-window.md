# ADR 0001: движок для первого окна Search

Статус: принято 17 ноября 2026 года **только для ограниченного экспериментального первого окна**. Решение не разрешает произвольный просмотр сайтов и не подтверждает готовность к выпуску.

## Контекст

Search нужен как браузер на macOS, Windows и Linux. Для первого рабочего этапа нужны обычные сайты, верхние вкладки, навигация и локальный профиль. Перед полезным выпуском дополнительно обязательны изоляция профилей, приватное хранение, понятные разрешения сайтов, загрузки, доступность и проверка на трёх ОС. Скорость не объявляется преимуществом без измерений.

Сравниваются два пути: Rust-оболочка Wry с системным WebView и встраиваемый Servo. [Платформенная матрица](../platform-matrix.md) содержит результаты узких прототипов, а [план](../prototype-plan.md) задаёт одинаковые сценарии для сравнения. Пока нет полной серии одинаковых сценариев и сопоставимых измерений. Поэтому выбор ниже ограничен первым окном для разработки, а не полезным браузером.

## Решение для первого экспериментального окна

Выбрать **Wry 0.57.1 с системным WebView** для первого экспериментального окна Search. Начальная сборка может открывать только собственную локальную тестовую страницу и заранее выбранные HTTPS-сайты. Это разрешает начать код приложения и проверять его компоновку, навигацию и вкладки. Это не разрешение принимать произвольные адреса, сохранять пользовательские профили или выпускать браузер для повседневного использования. Servo продолжать исследовать отдельно; замена движка потребует нового ADR.

Причина: Wry уже показал окно и переход на Mac, работу локального WebView2 на Windows CI и видимый ввод на Linux Xvfb. На Mac три открытых сайта достигли ограниченных [DOM-признаков](../experiments/2026-11-17-wry-public-sites.md). ServoShell v0.8.0 создал [снимки тех же сайтов](../experiments/2026-11-17-servo-public-sites.md), но в Excalidraw дважды возникла ошибка `indexedDB is not defined`; проверенное временное хранилище на Mac сохранило данные после перезапуска, а локальная загрузка не дала файла в проверенных каталогах. Это результаты конкретных версий и сценариев, не оценка всех возможностей движков. [Сводка](../platform-matrix.md), [профили Servo](../experiments/2026-11-11-servo-macos-profiles.md), [загрузка Servo](../experiments/2026-11-10-servo-macos-v080.md).

Сам [проект Servo](https://github.com/servo/servo) называет движок прототипом, а [документацию по встраиванию](https://book.servo.org/embedding/overview.html) считает незавершённой. Это не запрет на Servo в будущем, но увеличивает объём собственного сопровождения первой версии.

## Порог для кода первого экспериментального окна

Старый порог требовал завершить измерения, профили, разрешения, файлы и сбои до написания основного окна. Часть этих проверок требует самого окна и нескольких WebView. Чтобы получить проверяемый код без заявления о готовом браузере, разрешена только следующая ограниченная сборка:

1. Каждый WebView с содержимым сайта создаётся без постоянного профиля в режиме incognito и явно отклоняет чувствительные разрешения, скачивания и новые окна. Нет сохранённых решений о разрешениях и запроса с названием сайта. Новые WebView создаются только через одну проверенную конфигурацию. Сам флаг incognito не доказывает изоляцию вкладок и отсутствие следов на диске: до объединения первого окна провести отдельную отрицательную проверку данных.
2. Верхняя навигация принимает только точный локальный тестовый origin и фиксированный список HTTPS-origin с учётом редиректов; адреса с учётными данными и другие порты отклоняются. `file:`, пользовательские и внешние схемы не открываются. Обработчик верхней навигации не считается фильтром субресурсов страницы.
3. Недоверенная страница не получает Rust IPC, внутренние команды, пользовательские схемы или доступ к файлам. Панель Search и содержимое сайта имеют отдельные границы доверия.
4. На Windows для каждого WebView задаётся `with_additional_browser_args("")`, чтобы не передавать аргумент Wry 0.57.1, отключающий SmartScreen по умолчанию. Это не доказывает фактическую работу SmartScreen на физическом ПК.
5. Перед объединением первого окна: отрицательные проверки этих границ на локальных страницах, сборка и запуск на затронутых ОС, независимое QA и security-ревью. Если ограничение нельзя надёжно реализовать, приложение остаётся в исследовательском прототипе.

У Wry 0.57.1 настройки по умолчанию не подходят для этой границы: скачивание разрешено, обработчик разрешений отсутствует, режим incognito выключен. [Исходный код Wry](https://github.com/tauri-apps/wry/blob/wry-v0.57.1/src/lib.rs), [аргументы WebView2](https://github.com/tauri-apps/wry/blob/wry-v0.57.1/src/webview2/mod.rs).

## Порог для произвольных сайтов и полезного выпуска

1. Провести одинаковый локальный набор сценариев Wry и Servo на закреплённых версиях: навигация, вкладка/новое окно, файл на скачивание и загрузку, медиа, сбой страницы. Отдельно зафиксировать, какие сценарии проверены в GUI, а какие только headless или CI.
2. Продолжить проверку обычных сайтов на обеих основах без личных аккаунтов: выполнить действия внутри страницы и записать дату, видимый результат, ошибки и ограничения. Уже полученные DOM-признаки и снимки не доказывают работу поиска или веб-приложения.
3. Получить минимальные сопоставимые измерения запуска и памяти в одинаковом режиме на одном устройстве. Если режимы прототипов различаются, не сравнивать их как скорость движков; записать, почему измерение отложено.
4. Для Wry на каждой ОС и в каждом создаваемом WebView явно установить обработчик с отклонением чувствительных разрешений по умолчанию. Отрицательными тестами проверить камеру, микрофон и геолокацию в основном и новом окне. Пока нет достоверного origin фактического запроса, не показывать запрос с адресом верхней страницы и не сохранять разрешение для неё. Разрешение доступа и сохранённые решения остаются блокером полезного выпуска.
5. До открытия произвольных сайтов в первом окне проверить границу между страницей и Rust: страница не вызывает внутренние команды, не читает локальные файлы через `file:` или пользовательскую схему и не запускает внешнее приложение без подтверждения. Для `window.open` проверить наследование обработчика разрешений и остальных ограничений новым WebView.
6. На Windows явно переопределять дополнительные аргументы WebView2 пустой строкой вместо аргумента Wry 0.57.1, отключающего `msSmartScreenProtection` по умолчанию. До произвольного просмотра сайтов и полезного выпуска подтвердить конфигурацию и фактическое поведение SmartScreen на физическом Windows-ПК; успешный CI-запуск без этого недостаточен.

Эти пункты остаются открытыми после выбора основы первого окна. Они должны пройти отдельные опыты и ревью до соответствующих функций и выпуска. В частности, без достоверного origin фактического запроса нельзя давать разрешение камере, микрофону или геолокации; без проверки физического Windows-ПК нельзя объявлять защиту SmartScreen подтверждённой. Скорость не объявлять преимуществом до сопоставимого измерения.

## Риски и выпускные блокеры Wry

- Общий обработчик Wry получает вид разрешения без origin. На Linux наш изолированный опыт с камерой в cross-origin iframe дошёл до обработчика, но `PermissionStateQuery.security_origin` указывал верхний сайт. Значит, его нельзя подставлять в запрос пользователю как origin iframe. [Опыт Search](../experiments/2026-11-13-wry-linux-origin-permissions.md), [исходный код Wry 0.57.1](https://github.com/tauri-apps/wry/blob/wry-v0.57.1/src/webkitgtk/mod.rs), [публичный API WebKitGTK UserMediaPermissionRequest](https://webkitgtk.org/reference/webkit2gtk/stable/class.UserMediaPermissionRequest.html).
- Изоляция и удаление cookies, cache, storage, истории и разрешений на Windows и Linux не доказаны. Тест Mac покрывает только указанные тестовые маркеры.
- Windows CI не подтверждает видимые пиксели, пользовательский ввод и фактическую работу SmartScreen на физическом ПК. Wry 0.57.1 по умолчанию передаёт аргумент отключения `msSmartScreenProtection`; прототип Windows переопределяет дополнительные аргументы пустой строкой, но это ещё не проверка фактической защиты. [Опыт Windows](../experiments/2026-11-10-wry-windows-runtime.md).
- Linux Xvfb не подтверждает Wayland, экранный диктор и поведение на физическом компьютере.
- Нет одинаковых измерений скорости; до них не обещать прирост производительности.

## Что может изменить выбор

Если Wry не позволит безопасно показать и отозвать разрешения сайта на поддерживаемых ОС, не пройдёт изоляцию данных или обычные сайты, пересмотреть решение до полезного выпуска. Если Servo с зафиксированной версией пройдёт встраивание, приватное удаление данных, загрузки и сайты на трёх ОС, повторить сравнение через новый ADR. Не переносить результаты ServoShell на встраиваемую сборку без проверки.
