# ADR 0001: движок для первого окна Search

Статус: предложение, 13 ноября 2026 года. Это решение ещё не принято для основного приложения или выпуска.

## Контекст

Search нужен как браузер на macOS, Windows и Linux. Для первого рабочего этапа нужны обычные сайты, верхние вкладки, навигация и локальный профиль. Перед полезным выпуском дополнительно обязательны изоляция профилей, приватное хранение, понятные разрешения сайтов, загрузки, доступность и проверка на трёх ОС. Скорость не объявляется преимуществом без измерений.

Сравниваются два пути: Rust-оболочка Wry с системным WebView и встраиваемый Servo. [Платформенная матрица](../platform-matrix.md) содержит результаты узких прототипов, а [план](../prototype-plan.md) задаёт одинаковые сценарии для сравнения. Пока нет полной серии одинаковых сценариев и сопоставимых измерений.

## Предлагаемое решение

Выбрать **Wry для первого рабочего окна Search** после закрытия исследовательского порога ниже. Это выбор основы для этапа 1, а не утверждение, что Wry уже проходит требования к готовому браузеру. Servo продолжать исследовать отдельно; не обещать замену движка без нового ADR.

Причина предложения: Wry уже показал окно и переход на Mac, работу локального WebView2 на Windows CI и видимый ввод на Linux Xvfb. На Mac тестовые cookie и `localStorage` двух постоянных профилей и приватного окна разделились, а локальная загрузка прошла. ServoShell v0.8.0 отрисовал локальную страницу на трёх ОС, но проверенное временное хранилище на Mac сохранило тестовые данные после перезапуска; локальная загрузка на Mac не дала файла в проверенных каталогах. Это результаты конкретных версий и сценариев, не оценка всех возможностей движков. [Сводка](../platform-matrix.md), [профили Servo](../experiments/2026-11-11-servo-macos-profiles.md), [загрузка Servo](../experiments/2026-11-10-servo-macos-v080.md).

Сам [проект Servo](https://github.com/servo/servo) называет движок прототипом, а [документацию по встраиванию](https://book.servo.org/embedding/overview.html) считает незавершённой. Это не запрет на Servo в будущем, но увеличивает объём собственного сопровождения первой версии.

## Исследовательский порог перед принятием ADR и основным кодом

1. Провести одинаковый локальный набор сценариев Wry и Servo на закреплённых версиях: навигация, вкладка/новое окно, файл на скачивание и загрузку, медиа, сбой страницы. Отдельно зафиксировать, какие сценарии проверены в GUI, а какие только headless или CI.
2. Проверить несколько обычных сайтов на обеих основах без личных аккаунтов и записать дату, видимый результат, ошибки и ограничения. Успех локального HTML не равен совместимости сайтов.
3. Получить минимальные сопоставимые измерения запуска и памяти в одинаковом режиме на одном устройстве. Если режимы прототипов различаются, не сравнивать их как скорость движков; записать, почему измерение отложено.
4. Для Wry на каждой ОС и в каждом создаваемом WebView явно установить обработчик с отклонением чувствительных разрешений по умолчанию. Отрицательными тестами проверить камеру, микрофон и геолокацию в основном и новом окне. Пока нет достоверного origin фактического запроса, не показывать запрос с адресом верхней страницы и не сохранять разрешение для неё. Разрешение доступа и сохранённые решения остаются блокером полезного выпуска.
5. До открытия произвольных сайтов в первом окне проверить границу между страницей и Rust: страница не вызывает внутренние команды, не читает локальные файлы через `file:` или пользовательскую схему и не запускает внешнее приложение без подтверждения. Для `window.open` проверить наследование обработчика разрешений и остальных ограничений новым WebView.
6. На Windows явно переопределять дополнительные аргументы WebView2 пустой строкой вместо аргумента Wry 0.57.1, отключающего `msSmartScreenProtection` по умолчанию. До этапа 1 подтвердить конфигурацию и фактическое поведение SmartScreen на физическом Windows-ПК; успешный CI-запуск без этого недостаточен.

После порога другой агент проверяет доказательства, ограничения и этот ADR. Только затем менять статус на «принято» и отмечать переход к этапу 1 в [плане](../roadmap.md).

## Риски и выпускные блокеры Wry

- Общий обработчик Wry получает вид разрешения без origin. На Linux наш изолированный опыт с камерой в cross-origin iframe дошёл до обработчика, но `PermissionStateQuery.security_origin` указывал верхний сайт. Значит, его нельзя подставлять в запрос пользователю как origin iframe. [Опыт Search](../experiments/2026-11-13-wry-linux-origin-permissions.md), [исходный код Wry 0.57.1](https://github.com/tauri-apps/wry/blob/wry-v0.57.1/src/webkitgtk/mod.rs), [публичный API WebKitGTK UserMediaPermissionRequest](https://webkitgtk.org/reference/webkit2gtk/stable/class.UserMediaPermissionRequest.html).
- Изоляция и удаление cookies, cache, storage, истории и разрешений на Windows и Linux не доказаны. Тест Mac покрывает только указанные тестовые маркеры.
- Windows CI не подтверждает видимые пиксели, пользовательский ввод и фактическую работу SmartScreen на физическом ПК. Wry 0.57.1 по умолчанию передаёт аргумент отключения `msSmartScreenProtection`; прототип Windows переопределяет дополнительные аргументы пустой строкой, но это ещё не проверка фактической защиты. [Опыт Windows](../experiments/2026-11-10-wry-windows-runtime.md).
- Linux Xvfb не подтверждает Wayland, экранный диктор и поведение на физическом компьютере.
- Нет одинаковых измерений скорости; до них не обещать прирост производительности.

## Что может изменить выбор

Если Wry не позволит безопасно показать и отозвать разрешения сайта на поддерживаемых ОС, не пройдёт изоляцию данных или обычные сайты, пересмотреть решение до полезного выпуска. Если Servo с зафиксированной версией пройдёт встраивание, приватное удаление данных, загрузки и сайты на трёх ОС, повторить сравнение через новый ADR. Не переносить результаты ServoShell на встраиваемую сборку без проверки.
