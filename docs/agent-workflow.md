# Как работают агенты Search

Проектные роли описаны в `.codex/agents/`, их параллельность ограничена `.codex/config.toml`. [Документация Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents). Эти файлы задают поведение при новых запусках, но не создают отдельных учётных записей, не выдают доступ к GitHub и не делают ревьюера технически read-only. Доступы наследуются от основного сеанса.

## Перед задачей

Координатор проверяет этап проекта и заполняет [карточку задачи](task-template.md): цель, владельца файлов, исходные данные, критерии готовности и затронутые ОС. Исследование и ревью можно делать параллельно. Изменения общих файлов идут последовательно.

## Цикл изменения

1. Создать отдельную ветку от синхронизированной основной ветки и задачу в GitHub.
2. `researcher` проверяет зависимые API, если они влияют на решение.
3. `implementer` делает ограниченное изменение; до ADR из кода допустимы только исследовательские прототипы.
4. Автоматические проверки запускаются на затронутых ОС. После появления кода: формат, lint, тесты, сборка, UI smoke.
5. `qa_reviewer` проверяет поведение; `security_reviewer` подключается для изменений прав, данных, IPC, загрузок и обновлений. Для сложного Rust-кода добавляется отдельное ревью корректности. Ревьюер проверяет конкретный diff и критерии задачи, а не пересказывает работу автора.
6. Координатор объединяет повторяющиеся замечания. Спорные серьёзные находки проверяются по воспроизведению или отдельным экспериментом. Если ревью не запустилось или проверка не удалась, результат остаётся непроверенным. Автор исправляет подтверждённые находки, ревьюеры повторно проверяют. Координатор готовит PR с доказательствами и ограничениями.
7. Слияние после успешных проверок. Если тариф GitHub не позволяет обязательные rulesets, координатор вручную соблюдает тот же порядок и не обещает серверную блокировку.

## Минимальный отчёт агента

- Задача и проверенные файлы/версии.
- Что наблюдалось, чем проверено, на какой ОС.
- Что остаётся непроверенным.
- Находки с воспроизведением и серьёзностью или явное «находок в проверенных сценариях нет».

В PR приложить те же сведения, ссылку на задачу, список затронутых ОС и вывод проверок. Для нового дефекта добавить регрессионную проверку. Если проверка на одной из ОС недоступна, указать это прямо.

## Границы

Агенты не работают одновременно над одним файлом и не сливают собственные изменения без независимой проверки. Текст роли «не редактируй» служит инструкцией, а не ограничением прав на уровне ОС. [Codex multi-agent](https://developers.openai.com/api/docs/guides/agents-api/multi-agent) рекомендует давать независимые задачи и координировать общие файлы. [Codex Code Review](https://developers.openai.com/blog/custom-code-review-rules-for-codex) дополняет тесты и защиту веток, но не заменяет их.

## Что ещё требуется для полной работы

- После появления кода добавить сборку и тесты на трёх ОС и проверить реальный запуск ролей в новом сеансе Codex.
- Проверить работу правил основной ветки на тестовом PR.
