# Wry 0.57.1: аудит разрешений на macOS

Статус: проверены API и исходный код Wry, выполнены локальные проверки Rust. Реальный запрос камеры, микрофона или геолокации из страницы ещё не запускался.

## Что найдено

- Общий `with_permission_handler` принимает `PermissionKind` и возвращает `PermissionResponse`. Адрес сайта и frame в callback не передаются. [API Wry](https://docs.rs/wry/0.57.1/wry/struct.WebViewBuilder.html).
- В macOS-реализации WebKit вызывает delegate с `WKSecurityOrigin` и `WKFrameInfo`, но Wry 0.57.1 принимает их как `_origin` и `_frame` и не передаёт приложению. Если обработчик не задан, код возвращает `WKPermissionDecision::Grant` для запроса media capture. Системное разрешение macOS при этом остаётся отдельной границей. [Исходник Wry 0.57.1](https://github.com/tauri-apps/wry/blob/wry-v0.57.1/src/wkwebview/class/wry_web_view_ui_delegate.rs).
- `PermissionResponse::Deny` переводится в WebKit `WKPermissionDecision::Deny`. Для совмещённого запроса камеры и микрофона Wry отказывает, если хотя бы один ответ `Deny`. [Исходник Wry 0.57.1](https://github.com/tauri-apps/wry/blob/wry-v0.57.1/src/wkwebview/class/wry_web_view_ui_delegate.rs).
- `PermissionKind::Geolocation` в Wry помечен как пока не поддерживаемый на macOS/iOS. Обработчик Wry не служит доказанной защитой для геолокации. [Типы разрешений Wry](https://github.com/tauri-apps/wry/blob/wry-v0.57.1/src/permissions.rs).
- По документации Wry обработчик вызывается только для новых запросов. Если в постоянном WebView уже сохранено разрешение, движок может использовать его без вызова обработчика. Этот случай в прототипах не проверен. [API Wry](https://docs.rs/wry/0.57.1/wry/struct.WebViewBuilder.html).

## Решение для существующих прототипов

В обоих macOS-прототипах Search обработчик теперь явно возвращает `Deny` для каждого запроса, который Wry передаёт ему. Unit-тесты проверяют отказ для `Camera` и `Microphone`; CI запускает эти тесты. Это временная политика исследовательских окон, а не готовое управление разрешениями сайтов. Поведение браузера и системного запроса в реальном UI ещё нужно проверить.

## Что нужно до архитектурного решения

1. В отдельном опыте открыть два локальных origin и cross-origin iframe. Запросить media capture, не предоставляя доступ к устройствам, и проверить, какой origin и frame сообщает WebKit. Отдельно проверить профиль с ранее сохранённым решением.
2. Проверить origin-aware обработчик на уровне Wry patch/fork или официально поддержанного API. Простая замена `WKWebView.uiDelegate` может нарушить другие обработчики Wry, включая окна и выбор файлов.
3. Проверить геолокацию и остальные разрешения отдельно на каждой ОС. Если нельзя надёжно привязать решение к сайту, сценарий разрешений из технического задания не пройден.

Вывод: общий API Wry 0.57.1 сам по себе не даёт Search показать корректный запрос разрешения именно для запрашивающего сайта. Требуется проверенное платформенное решение или иной путь для движка.

Первый [реальный запрос камеры](2026-11-07-wry-camera-deny-runtime.md) не достиг обработчика Wry после того, как владелец отклонил системный запрос macOS. Он не подтверждает и не опровергает работу `Deny` на уровне WebKit.
